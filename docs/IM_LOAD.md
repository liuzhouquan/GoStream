# IM 两实例负载工作包

基线：`b9957ea`。本工作包验证 A07 单聊负载与恢复，不关闭整个 A07，也不替代同一性能表中的十个真实视频处理及最终全组件 Compose/浏览器验收。

## 固定范围与退出条件

- 真实生产 API 两进程、独立 MySQL/Redis 连接；随机空 schema/专用用户和临时 Redis，拒绝复用演示数据。
- 先通过正式注册接口创建全部账户，遇到共享 Redis 的 10 次/分钟限制则按真实 Retry-After 有界等待，准备耗时单独记录，不关闭限流、不伪造转发头；注册完再建立连接。
- 20 个不同账户、一账户一条 WebSocket，两个进程各 10 条；每账户串行发送 50 条消息，20 个发送者并发，收件人位于另一个进程。每轮 1,000 条、256 字节正文、最多 20 条等待发送 ACK 的消息，运行三轮，不将此闭环负载视为最大吞吐。
- 逐帧校验 sender/recipient/body/client_id/server ID，完整统计 1,000 个发送 ACK 和 1,000 个接收消息；任意错误、未知 ID、错收件人、同键不同 ID、连接丢失或超时都失败。实时提示可重复，但重复帧单独统计，SQL 的消息身份必须唯一。
- 单调时钟记录写入前到发送 ACK、写入前到接收事件的客户端延迟，保留每条原始样本、P50/P95/P99/max、测量时长与数量；不设置未经验证的绝对毫秒阈值。
- 采样两个 API 的 Prometheus 进程 CPU、RSS、goroutine 和 WebSocket 连接数。CPU 是进程累计值差；RSS 为采样峰值，不是精确内核峰值。记录每次 scrape_ms 及累计 HTTP 抓取墙钟耗时（包含服务端处理与客户端读取，不据此从 CPU/延迟中扣减）、构建是否开启 race、宿主机 CPU/内存及组件版本。MySQL/Redis CPU 不据此声称已测量。
- 每轮通过另一个 API 查询精确未读集合并逐设备 ACK，随后重复至少一次发送，要求返回原 ID；SQL 最终核对每条身份和正文，不只检查总数。
- 关闭一条接收连接，再提交 125 条消息；重连同设备只重放 100 条并发同步标记，完整未读及 425 条双向会话历史以 37 条分页核对、ACK 后为零，新设备保留独立积压。最终 SQL 为 3,125 条唯一消息。
- 负载只使用生产公开 HTTP/WebSocket 接口；SQL 只做隔离前置检查、通知队列排空和最终状态核对，不生成或改写业务数据。报告不包含 JWT/密码/DSN。
- 外层启动器管理子进程组，正常/失败/超时后都先停进程，再移除 Redis、SQL、临时目录，核对零残留。CI 对最终提交运行现有普通/race/真实组件矩阵与本负载。

## 执行入口

```sh
python3 tests/integration/im_smoke.py \
  --go-bin /usr/local/go/bin/go \
  --mysql-container gostream-mysql-1 \
  --mysql-addr 127.0.0.1:3307 \
  --suite load --report-file /tmp/gostream-im-load.json
```

默认 recovery 模式维持原来的 API/test race 构建；load 默认常规构建。`--race-load` 仅用于单独的竞态回归，结果标注 race，不与常规延迟混合。`--check-timeout-cleanup` 只允许 recovery。直接 Go 入口必须显式设置负载开关与隔离环境，普通本地测试跳过。

单机回环 CI 的数据不能推算生产容量；没有群聊扇出、媒体、长稳态运行或跨主机网络测量。


## 实测与环境

候选 `1f84780` 的 [CI 41178501091](https://github.com/liuzhouquan/GoStream/actions/runs/41178501091) 八项任务通过。环境为 GitHub-hosted Ubuntu 24.04、Linux 7.0.0-1017-azure x86_64、AMD EPYC 7763、4 个可见 vCPU、约 15.61 GiB 内存、Go 1.27.2、MySQL 8.4.13、Redis 8.2.9。API 和驱动/数据库在同一 runner 上；未启用 RabbitMQ、FFmpeg 或对象存储，通知走生产 SQL outbox/Redis 路径。无模拟 API 或数据库写入夹具。

[摘要 JSON](benchmarks/im-load-summary-2026-10-31.json) 保存构建、宿主机、每轮指标和原始文件 SHA-256；[常规原始报告](benchmarks/im-load-2026-10-31.json.gz) 与 [race 原始报告](benchmarks/im-load-race-2026-10-31.json.gz) 为 CI artifact 的无损 gzip 副本，包含全部 6,000 对 ACK/投递样本和进程采样。报告的 checkout_revision 是 CI 实际 checkout 的 PR 合并候选 SHA；摘要另外记录来源分支 head。解压后可用 Python 标准库读取：

```python
import gzip, json
with gzip.open("docs/benchmarks/im-load-2026-10-31.json.gz", "rt") as source:
    report = json.load(source)
print(report["rounds"][0]["recipient_delivery"])
```

三轮各有 1,000 个发送 ACK、1,000 个完整接收事件，观察窗口内重复 ACK/投递均为 0。常规构建另有 60 次原键重试，SQL 保持 3,000 条在线消息；追加 125 条离线消息后最终精确核对 3,125 条唯一身份/正文。重连同设备得到 100 条重放和 sync_required，未读补齐 125 条、双向历史补齐 425 条、ACK 重试新增 0、新设备保留 275 条独立未读。race 构建在另一个空 schema/Redis 上完成同样三轮及所有断言，没有竞态报告；race 延迟不并入上表。

注册阶段常规构建按真实限流等待约 18.001 秒，race 构建约 6.005 秒，均在连接建立和测量之前。两个 API 每轮始末及采样时各维持 10 条连接。CPU 差值含后台 outbox、Redis 桥和指标抓取；常规每轮累计两 API 的抓取墙钟约 0.35–0.40 秒，与发送并发且不能直接从时长/CPU中扣减。采样为目标 100ms，实际间隔与每次耗时已保留。数据库/Redis/驱动的 CPU、进程精确内存峰值未测。

ACK P95 约 38–42ms，而接收 P95 约 426–497ms，说明这两个确认阶段不能混为一个延迟。具体延迟组成尚未通过 profiler 定位，不把 Redis/SQL 的某个猜测写成已确认瓶颈。此为短时闭环负载，没有持续时长、开环到达率或容量对照，不能据此宣称平台最大 QPS、跨主机性能或长时间稳定性。

正常负载、race 负载、原有恢复矩阵和故意超时退出均经外层检查零残留进程、schema、用户和 Redis 容器；只有测试及清理都成功后才发布 JSON。首次候选 `7d81643` 的 [CI 41178262334](https://github.com/liuzhouquan/GoStream/actions/runs/41178262334) 在正式注册收到 429 后失败，失败清理仍为零残留；未发布成功负载报告。
