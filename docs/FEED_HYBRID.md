# Following Feed: bounded push and pull

The following Feed can use two read sources. Videos from authors with at most `FEED_FANOUT_MAX_FOLLOWERS` followers at publication get a durable `feed_fanout_jobs` row in the same transaction that publishes the video. The author threshold query reads at most `threshold + 1` follower IDs. The worker writes one `feed_inboxes` row per follower in batches of 128. Authors above the threshold stay on the direct video/follow join. The default is `0` (SQL-only) while the 20% end-to-end P95 target remains unmet; set `1000` to exercise the hybrid strategy. The accepted range is `0..100000`. A video's choice is made when it becomes published and does not change retroactively.

The worker leases a job with a conditional update, stores its last scanned follower ID, and marks it complete only after a final empty batch. A restart can replay a batch; `(user_id, video_id)` uniqueness makes insertion idempotent. An expired lease can be claimed by another instance. On an error, the job records a short message and retries with capped backoff. There is no dead-letter cutoff for this index: while a job is unfinished, the read path uses the author pull query, so a permanently failing job does not hide public videos. Operators can inspect `SELECT video_id, last_follower_id, attempts, available_at, lease_until, done_at, last_error FROM feed_fanout_jobs WHERE done_at IS NULL ORDER BY id;` for backlog and errors.

The v004 `videos.feed_pull` flag is true for high-follower, legacy and unfinished videos. A completed worker flips it to false in the same transaction that marks its job done. The indexed read now takes at most `limit + 1` rows from each of three branches: flagged pull videos, completed videos older than a newly created follow, and inbox entries. A SQL `UNION` deduplicates IDs before the final video-card query. The inbox branch checks the *current* follow relation and publication state, so unfollow or deletion takes effect without deleting old inbox rows. The late-follow branch preserves access to older posts after following or re-following an author. The opaque cursor carries timestamp, ID, scene and time-zone offset. Redis still caches only a viewer's first following page for five seconds; follow/unfollow and publication invalidate it as before.

The v003 migration creates the job/inbox tables and indexes. The additive v004 migration adds the pull flag and index, then idempotently backfills completed jobs; it can retry after interrupted DDL. Existing old-version workers can still finish jobs safely because a true flag causes extra pull reads, not missing videos. `platform.MigrateSchema` remains for test and legacy fixtures; production startup applies the numbered SQL snapshots. The MySQL backup/restore drill removes v004, v003 and v002 markers before rehearsing a v002 forward migration.

Tests cover synchronous and FFmpeg publication, high/low follower branches, visibility before and after fanout, late follow, unfollow, one-item cursor pages, batch replay, and migration retry/backfill. A disposable MySQL 8.4 database verifies equal-timestamp cursor pages. A second committed MySQL fixture uses two independent database connections: instance A writes one 128-follower batch; an abandoned active lease blocks instance B; after expiry B replays and completes the 130-follower job without duplicate inbox rows or a Feed visibility gap. This simulates lease takeover, not an actual API process crash. The worker exposes completed/batch/error counters, completion latency, and a pending-job gauge sampled every 30 seconds. A real 38-follower job completed in 2.201 seconds. The first 2,000-user comparison found the v003 hybrid read slower than SQL-only; the v004 indexed query improved SQL execution, but the full HTTP P95 gain was only about 11% for a viewer following both ordinary and high-follower authors and about 4% for an ordinary-only viewer in three alternating runs. A small mixed read/write smoke now exists; details and limits are in [`PERFORMANCE.md`](PERFORMANCE.md). The default remains SQL-only while the 20% A04 target is unmet. Inbox rows currently have no retention policy. SQLite mixed-offset legacy timestamps can still sort by textual wall time rather than absolute time. A04 remains open for full-size mixed read/write, actual two-process failure, 60-second backlog drain under load, and further end-to-end optimization.

## 2026-10-31 hybrid query optimization

The Following Feed query in `following_feed.go` previously executed a preliminary `SELECT EXISTS(SELECT 1 FROM follows WHERE follower_id = ?)` round-trip before executing the 3-subquery UNION. This incurred an extra synchronous database network round trip on every following-feed request for active viewers. The query path now directly executes the pre-allocated UNION query (`sql.Grow(1024)`, `make([]any, 0, 16)`). When a viewer has zero followed authors, each of the three subquery branches naturally matches zero rows, returning an empty video slice in a single round trip without error or extra overhead. In-process benchmark `BenchmarkFollowingFeed` in `feed_bench_test.go` measures in-memory SQLite performance, while MySQL 20,000-video execution benefits from saving one full round-trip per request.
