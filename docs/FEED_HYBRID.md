# Following Feed: bounded push and pull

The following Feed can use two read sources. Videos from authors with at most `FEED_FANOUT_MAX_FOLLOWERS` followers at publication get a durable `feed_fanout_jobs` row in the same transaction that publishes the video. The author threshold query reads at most `threshold + 1` follower IDs. The worker writes one `feed_inboxes` row per follower in batches of 128. Authors above the threshold stay on the direct video/follow join. The default is `0` (SQL-only) while the 20% end-to-end P95 target remains unmet; set `1000` to exercise the hybrid strategy. The accepted range is `0..100000`. A video's choice is made when it becomes published and does not change retroactively.

The worker leases a job with a conditional update, stores its last scanned follower ID, and marks it complete only after a final empty batch. A restart can replay a batch; `(user_id, video_id)` uniqueness makes insertion idempotent. An expired lease can be claimed by another instance. On an error, the job records a short message and retries with capped backoff. There is no dead-letter cutoff for this index: while a job is unfinished, the read path uses the author pull query, so a permanently failing job does not hide public videos. Operators can inspect `SELECT video_id, last_follower_id, attempts, available_at, lease_until, done_at, last_error FROM feed_fanout_jobs WHERE done_at IS NULL ORDER BY id;` for backlog and errors.

The v004 `videos.feed_pull` flag is true for high-follower, legacy and unfinished videos. A completed worker flips it to false in the same transaction that marks its job done. The indexed read takes at most `limit + 1` rows from each of three branches: flagged pull videos, completed videos older than a newly created follow, and inbox entries. These branches are disjoint: the late-follow branch excludes videos already in that viewer's inbox, and the inbox branch accepts only videos whose fanout is complete (`feed_pull = false`). The query can therefore use `UNION ALL` without a distinct sort. The inbox branch checks the *current* follow relation and publication state, so unfollow or deletion takes effect without deleting old inbox rows. The late-follow branch preserves access to older posts after following or re-following an author. The opaque cursor carries timestamp, ID, scene and time-zone offset. Redis still caches only a viewer's first following page for five seconds; follow/unfollow and publication invalidate it as before.

The v003 migration creates the job/inbox tables and indexes. The additive v004 migration adds the pull flag and index, then idempotently backfills completed jobs; it can retry after interrupted DDL. Existing old-version workers can still finish jobs safely because a true flag causes extra pull reads, not missing videos. `platform.MigrateSchema` remains for test and legacy fixtures; production startup applies the numbered SQL snapshots. The MySQL backup/restore drill removes v004, v003 and v002 markers before rehearsing a v002 forward migration.

Tests cover synchronous and FFmpeg publication, high/low follower branches, visibility before and after fanout, late follow, unfollow, one-item cursor pages, batch replay, and migration retry/backfill. A disposable MySQL 8.4 database verifies equal-timestamp cursor pages. A second committed MySQL fixture uses two independent database connections: instance A writes one 128-follower batch; an abandoned active lease blocks instance B; after expiry B replays and completes the 130-follower job without duplicate inbox rows or a Feed visibility gap. This simulates lease takeover, not an actual API process crash. The worker exposes completed/batch/error counters, completion latency, and a pending-job gauge sampled every 30 seconds. A real 38-follower job completed in 2.201 seconds. The first 2,000-user comparison found the v003 hybrid read slower than SQL-only; the v004 indexed query improved SQL execution, but the full HTTP P95 gain was only about 11% for a viewer following both ordinary and high-follower authors and about 4% for an ordinary-only viewer in three alternating runs. The full-size six-run A04 mixed read/write workflow has now run: all requests, publications, counter checks, Feed visibility checks, and fanout/outbox drains passed, but Hybrid following P95 was 36.82% slower than SQL-only. The 20% performance target failed, so the default remains SQL-only. Results and an explicitly exploratory late-follow diagnosis are in [`PERFORMANCE.md`](PERFORMANCE.md) and its [machine-readable summary](benchmarks/feed-a04-mixed-2026-11-02.json). Inbox rows currently have no retention policy. SQLite mixed-offset legacy timestamps can still sort by textual wall time rather than absolute time. A04 remains open for a verified performance improvement, Redis cache/failure behavior, and two-instance failure coverage.

The original mixed-load run used 20 workers but only 10 reader accounts, with two workers sharing each account and write target. Its P95 result is valid for that exact workload but is confounded by shared-identity writes. The acceptance runner now provisions one reader identity and untouched test video per worker while splitting login requests across the API's 30-per-minute limit. The corrected full-size run [#41566643755](https://github.com/liuzhouquan/GoStream/actions/runs/41566643755) used 20 distinct readers; every request, publication, counter, Feed visibility, outbox and fanout check passed, but Hybrid median following P95 was 68.163 ms versus SQL-only 53.055 ms (28.48% slower). This confirms the performance gate remains open under independent actors, but does not isolate a query-level cause. Full results and limitations are in [`PERFORMANCE.md`](PERFORMANCE.md) and [`benchmarks/feed-a04-mixed-2026-11-03.json`](benchmarks/feed-a04-mixed-2026-11-03.json); keep SQL-only as the default.

## 2026-10-31 hybrid query-count change

`followingVideos` now executes its UNION directly, removing the prior EXISTS query for active viewers; author preloading remains a separate query when results exist. Zero-follow viewers still obtain an empty list, but run the UNION instead of a cheap EXISTS, so their SQL-cost tradeoff needs measurement. The default remains SQL-only (`FEED_FANOUT_MAX_FOLLOWERS=0`). No MySQL latency gain is inferred from query count alone.

`BenchmarkFollowingFeed` compares current SQL-only and hybrid modes over 500 SQLite videos with a completed inbox, not the optimization's before/after versions. It explicitly updates and checks `feed_pull=false` after GORM insertion, sets the follow before publication, checks the exact 20 IDs/cursor and closes the SQL pool. Initial fixture validation failed with all 500 flags true because GORM applied `default:true`; the original fixture also selected the late-follow branch. In three corrected 100-operation runs, SQL-only was 440067/428639/406127 ns/op and hybrid was 866695/825537/789622 ns/op on the local Ryzen 7 5800H / Go 1.27.2 host. These are in-process handler timings with no MySQL/network/Redis, not QPS, P95 or a performance improvement claim. Full MySQL comparisons and A04's 20% threshold remain open.

## 2026-11-02 disjoint hybrid read branches

`followingVideos` uses `UNION ALL` after making source membership explicit. The unfinished/pull branch includes `feed_pull=true`; the inbox branch requires `feed_pull=false`; and the late-follow branch requires `feed_pull=false` plus no inbox row for the same viewer/video. This handles an in-progress fanout that has already inserted some inbox rows and a follower added during a fanout batch. `TestHybridFollowingMergesOverlappingSourcesOnce` exercises both overlaps through the public following Feed endpoint and checks exact ordering, no duplicate IDs, and the terminal `has_more` value. Removing either exclusion while retaining `UNION ALL` makes this test return duplicate IDs.

On the local Go 1.27.2 / Ryzen 7 5800H Linux/amd64 environment, three 100-iteration runs of the existing 500-video SQLite HTTP-handler benchmark had hybrid medians of 742093 ns/op before and 706417 ns/op after (4.8% lower); SQL-only medians were 382460 and 382524 ns/op. Hybrid allocations changed from 1219 to 1220–1221 per operation. [Raw command output and environment](benchmarks/following-union-all-2026-11-02.txt). This is a small in-process result, not MySQL HTTP latency or an A04 pass. The recorded full-size MySQL comparison remains about 11% / 4% P95 improvement, below the 20% gate; complete-size 20-concurrency runs and mixed-load/fanout measurements remain required.
