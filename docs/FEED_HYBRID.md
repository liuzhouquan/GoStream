# Following Feed: bounded push and pull

The following Feed now has two read sources. Videos from authors with at most `FEED_FANOUT_MAX_FOLLOWERS` followers at publication get a durable `feed_fanout_jobs` row in the same transaction that publishes the video. The author threshold query reads at most `threshold + 1` follower IDs. The worker writes one `feed_inboxes` row per follower in batches of 128. Authors above the threshold stay on the direct video/follow join. Set the threshold to `0` to use the former SQL-only query as a comparison baseline; the default is `1000` and the accepted range is `0..100000`. A video's choice is made when it becomes published and does not change retroactively.

The worker leases a job with a conditional update, stores its last scanned follower ID, and marks it complete only after a final empty batch. A restart can replay a batch; `(user_id, video_id)` uniqueness makes insertion idempotent. An expired lease can be claimed by another instance. On an error, the job records a short message and retries with capped backoff. There is no dead-letter cutoff for this index: while a job is unfinished, the read path uses the author pull query, so a permanently failing job does not hide public videos. Operators can inspect `SELECT video_id, last_follower_id, attempts, available_at, lease_until, done_at, last_error FROM feed_fanout_jobs WHERE done_at IS NULL ORDER BY id;` for backlog and errors.

The API reads up to `limit + 1` candidates from each branch, merges by `(videos.created_at DESC, videos.id DESC)`, removes duplicate IDs, and loads the final video cards and authors. The push branch joins each inbox row to the *current* follow relation and published video, so unfollow or deletion takes effect without deleting inbox rows. The pull branch includes high-follower authors, legacy videos without jobs, unfinished jobs, and videos created before a new follow. This last case preserves access to older posts after following or re-following an author. Cursor pages use the same two-branch merge; the opaque cursor carries the timestamp, ID, scene, and time-zone offset. The offset preserves SQLite's stored timestamp representation across pages. Redis still caches only a viewer's first following page for five seconds; follow/unfollow and publication invalidate it as before.

The v003 migration creates both tables, their unique keys, an inbox paging index, and a pending-job index. It is additive to v001/v002 and retries after interrupted DDL. `platform.MigrateSchema` includes these tables for test and legacy fixtures; production startup applies the numbered SQL snapshots. The MySQL backup/restore drill removes both v003 and v002 markers before rehearsing a v002 forward migration, then replays v003.

Tests cover synchronous and FFmpeg publication, high/low follower branches, visibility before and after fanout, late follow, unfollow, one-item cursor pages, batch replay, and migration retry. A disposable MySQL 8.4 database also verifies the two-branch query with equal video timestamps. These are correctness tests; the A04 load target has **not** yet been measured. The current implementation keeps inbox rows indefinitely and still evaluates a pull query on every following page. SQLite stores offsets in timestamp text; the cursor retains the offset of its last row, but a database with mixed-offset legacy timestamps can still sort by textual wall time rather than absolute time. Normalizing those older rows requires a separate migration. Write amplification and query plans need measurement with the delivery-scope dataset before claiming a performance benefit or marking A04 complete.
