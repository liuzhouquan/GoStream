## 3. 性能和恢复数据边界

- 可引用的既有完整无缓存A04基线：run [41803621425](https://github.com/liuzhouquan/GoStream/actions/runs/41803621425)，三轮中位Following P95为26.250ms，对照46.051ms，改善43%。这是该夹具的无缓存混合读写对照，不是暖缓存或多主机容量结论。
- G07原报告记录的是10作者/120视频、SQLite/miniredis、5秒预热/10秒烟测，所谓三轮轮换Following/Timeline/Hot各一次。它不能关闭G07正式门槛；脚本现在明确只提供组件smoke，未实现的完整standard模式拒绝执行。
- 本轮另补真实MySQL/Redis双API有界群负载：20客户端、1000消息、19000接收投递，接收P95为186.796ms；结果仅适用本轮单机夹具，见审查JSON。
- G08原报告是SQLite/miniredis有界群负载，不支持“200人、80+设备、P95 8.2ms”声明。正式群扇出结果须按实际成员/连接/消息ID集合重新测量。
- G10原报告的4.57ms是5用户/10视频/约4MiB本地文件的恢复阶段，既不是完整服务恢复时间，也不是MySQL/MinIO RTO。生产配置的恢复耗时、空间与一致性必须另外测量。
- 原报告中Feed P95 0.73–4.21ms、200人/80+设备群聊P95 8.2ms、生产RPO=0s/RTO=4.57ms等无对应可核对证据的声明已撤回，不应写入README或简历。
