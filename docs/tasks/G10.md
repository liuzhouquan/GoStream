## 4. 遇到的问题与解决方案

1. **分片上传大小对齐与 MP4 格式校验**：
   - *问题*：分片上传对中间分片有固定的 4 MiB 大小约束（`uploadChunkSize = 4 << 20`），且文件完成时服务端会校验首部分片的媒体魔数（`ftypisom`）。最初在构造断点续传样本时未对齐 4 MiB 边界且首分片未置入魔数，导致 `complete` 返回 400。
   - *方案*：第一分片填充精确的 4 MiB 且首部包含标准 MP4 文件头，第二分片作为尾部数据在恢复后上传，完美复原断点续传全流程。
2. **Go 内部包导入路径限制**：
   - *问题*：最初尝试在临时目录动态生成 Go 代码导入 `internal/migrations` 执行二次重放验证，触发 Go 编译器的 `use of internal package ... not allowed` 规则拦截。
   - *方案*：直接复用编译好的服务实例重新对恢复库发起拉起。由于 `cmd/gostream` 在启动时原生内置调用 `migrations.Apply`，天然实现了生产就绪重放验证。
3. **辅助标记键值解析**：
   - *问题*：`schema_migrations` 表中除 `schema_v001` - `schema_v005` 外，还包含设备迁移标记 `message_devices_v1`。
   - *方案*：采用子集包含（`issubset`）断言策略，既严格核对 5 大版本全量存在，又兼容合法的数据回填标记。
4. **在线热备假象与规范约束**：
   - *问题*：分布式架构下未配置协调快照时，仅做 SQL dump 容易与正在上传的对象存储发生时间差裂脑。
   - *方案*：在 `docs/OPERATIONS.md` 中严正声明不支持无停写在线热备，必须在停写维护窗口执行一致性快照；在测试中强制检验 `media_transfer_smoke.py` 与 `mysql_recovery.sh` 的单事务快照与对象恢复闭环。

## 5. CLOSE-03 审查缺陷与回归修复 (2026-11-11)

- **缺陷发现**：在 `CLOSE-03` 对 `tests/integration/migration_backup_recovery_smoke.py` 的逐行审查中，发现 `verify_quiescence` 的 HTTP 停写端口检测将 `raise RuntimeError("quiescent boundary check failed: ...")` 置于 `try: ... except Exception: pass` 内部，导致源端 API 仍在返回 200 OK 时异常被静默吞掉；且 Compose 双 API 模式下仅探测了 `self.base_url`，未同时检查 `self.owned_stack.api_b`。另 SQLite 模式统计备份文件数时未过滤目录条目。
- **修复前复现（TDD）**：在 `tests/diagnostics/test_recovery_isolation.py` 新增 `test_verify_quiescence_rejects_responding_source_api`，先运行验证确实失败（`AssertionError: RuntimeError not raised`）。
- **修复与验证**：将连接拒绝检查收窄为仅捕获 `(OSError, URLError)`，在 HTTP 状态非 503 或响应头非空时抛出 `RuntimeError` 且按序校验 `[self.base_url, api_a, api_b]`，并过滤文件对象数；修后全量 117 项诊断单测与 `migration_backup_recovery_smoke.py --mode sqlite` 实机停写检查全量通过。
