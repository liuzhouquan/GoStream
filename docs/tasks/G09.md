## 2. 范围、不变量与依赖

- **实现范围**：
  1. `internal/platform/component_outage_continuous_test.go`：
     - 原生 Go 自动化组件故障与持久化回归测试套件：
       - `TestComponentOutage_HealthAndReadySemantics`：
         - 验证 `/health` 恒定反映进程存活活性（HTTP 200 OK）；
         - 验证 `/ready` 严格由底层 SQL 数据库连接活性决定（SQL 可用返回 200，SQL 关闭或不可达返回 503 `database unavailable`）；
         - 验证 Redis、RabbitMQ、MinIO 等外部组件离线不改变 `/ready` 的 200 就绪语义，严禁语义漂移。
       - `TestComponentOutage_RedisFeedFallbackAndIMPersistence`：
         - 验证 Feed 暖缓存命中；Redis 突发离线时，Feed 缓存熔断器被动触发，Feed 全部场景（`timeline`、`following`）无缝回源至底层 SQL（HTTP 200 OK），数据无丢失、无截断；
         - Redis 离线期间，通过 WebSocket 发送私聊与群聊消息，SQL 事务原子持久化、发送端准时收到 ACK 帧，跨实例实时桥接失败不干扰业务事务；接收方通过 SQL 历史拉取（`GET /api/messages`）与未读计算（`GET /api/messages/unread`）获得 100% 准确数据；
         - Redis 恢复后，熔断冷却重置，Feed 重新命中暖缓存，Realtime 广播桥接自动重连。
       - `TestComponentOutage_RabbitMQOutboxPersistenceAndRecovery`：
         - 验证 RabbitMQ 离线时，点赞、评论等互动业务请求在 SQL 事务中正常提交，计数器与明细准确入库；
         - `OutboxEvent` 事件行以 `published_at IS NULL` 状态安全滞留数据库；Outbox worker 遇到 Broker 异常自适应退避与记录 `last_error`，绝不崩溃服务或丢弃事件；
         - RabbitMQ 恢复后，Outbox worker 自动排空待发事件并标记 `published_at IS NOT NULL`；
         - 消费端 `acceptBrokerNotification` 幂等消费，创建 `broker-delivery:*` 交付任务，防重保证 0 重复通知。
       - `TestOutage_MinIOStorageUnavailableAndNoOrphanSQL`：
         - MinIO 离线时分片上传返回 503 (`media storage unavailable`)；
         - 严格保持 SQL 不变量：`upload_chunks` 零脏行，`media_assets` 零多余记录，会话状态保持 `"open"`；
         - MinIO 恢复后分片成功续传并完成，跨实例重复完成保持幂等（返回相同 URL，无第二条资产记录）。
       - `TestComponentOutage_WorkerRestartAndLeaseReclaim`：
         - 活跃完成或 Outbox 处理 worker 崩溃后租约过期（`lease_until < now`），重启或新 worker 安全接管租约并成功完成，旧租约过期 worker 提交被栅栏机制完全阻断（0 rows affected）。

- **必须保持的不变量**：
  - **活性与就绪语义隔离**：
    $$\text{HealthStatus} = 200 \iff \text{ProcessIsAlive}$$
    $$\text{ReadyStatus} = 200 \iff \text{SQLDB.Ping}() == \text{nil}$$
    Redis、RabbitMQ、MinIO 异常绝不导致 `/ready` 虚假下线，SQL 不可用时必须快速返回 503。
  - **业务一致性与回源保底**：
    - Feed 缓存为非关键路径，Redis 宕机时自动降级回源至 SQL，保证 200 响应与数据正确性。
    - IM 消息与未读状态以 SQL 为最终一致性事实来源，实时广播失败不影响消息持久化与 ACK 返回。
    - 异步事件采用事务 Outbox 模式，业务提交必定保证事件持久化；Broker 恢复后自动重投，消费端严格按 `EventID` 幂等消费，无重复交付。
  - **故障隔离与零脏数据**：
    - 存储故障时快速失败（503），底层数据库绝不创建孤儿资产记录或错误分片元数据。
    - 租约与单调世代机制确保崩溃恢复后无双重处理，旧 Worker 提交彻底失效。

## 4. 遇到的问题与解决方案

1. **未读消息与历史记录 API 字段对齐**：
   - *问题*：测试客户端在校验 `GET /api/messages` 与 `GET /api/messages/unread` 时，误用 `"messages"` 与 `"unread_count"` 字段解析，导致断言失败。
   - *方案*：核对 `internal/platform/messages.go` 源码，两个接口均统一使用 `gin.H{"items": rows, "next_cursor": next, "has_more": more}` 分页格式，修正客户端解析模型。
2. **通知响应结构与用户画像字段对齐**：
   - *问题*：`GET /api/notifications` 返回结构为 `{"items": [...]}`，而 `GET /api/users/me` 直接序列化 `User` 模型；在断言中使用错误嵌套键值抛出 `KeyError`。
   - *方案*：核对 OpenAPI 契约与 Gin 路由实现，分别适配为 `items` 列表与顶级 `id` 属性。
3. **本地分片上传目录路径特征**：
   - *问题*：最初尝试在本地测试通过 `chmod 0555 media/uploads` 模拟存储写入错误，但分片上传实际上存放在 `s.uploadDir(id) = filepath.Clean(s.MediaDir) + ".chunks"` 路径下。
   - *方案*：准确将只读权限施加在 `${media_dir}.chunks` 目录上，成功触发 `media storage unavailable` 隔离错误并验证零脏数据不变量。
