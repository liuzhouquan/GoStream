- **必须保持的不变量与数学集合公式**：
  - **大群扇出集合模型**：
    - 设群成员规模为 $N=20$，群内任意成员 $i$ 发送消息 $m$，则接收该消息的合法成员集合为 $R(m) = \{ j \mid 1 \le j \le N \land j \neq \text{Sender}(m) \}$，扇出因子恒为 $N - 1 = 19$。
    - 客户端 $k$ 的期望接收消息 ID 集合严格定义为：
      $$E(k) = \{ m.\text{ID} \mid m \in \mathcal{M}_{\text{group}} \land m.\text{Sender} \neq k \}$$
    - 发送者 $k$ 对自己发出的消息只接收 1 次发送端 ACK 确认帧（`type: "ack"`, 携带 `client_id` 与分配的 `message_id`），绝不在接收流中收到自身广播（$\forall m \in \text{Received}(k), m.\text{Sender} \neq k$）。
    - 严格断言全局无重复接收与无重复 ACK：
      $$\text{DuplicateDeliveries} = 0, \quad \text{DuplicateACKs} = 0$$
  - **幂等性不变量**：
    - 重复提交相同的 `client_id` 触发幂等拦截，直接返回原消息已分配的 ACK 帧，数据库消息表行数不增加，且不触发二次扇出广播。
  - **离线与历史分页单调性**：
    - 离线成员累积消息数严格满足 $\Delta \text{Unread} = \text{Count}(\{ m \mid m.\text{ID} > \text{LastReadID} \land m.\text{Sender} \neq \text{OfflineUser} \})$。
    - 重连上限 100 条，超出部分下发 `group_sync_required`。通过 `GET /api/groups/:id/messages?before_id=...` 拉取的数据严格保持 ID 单调递减排列，与已推送数据零重叠、零遗漏。
  - **多设备隔离性**：
    - 每个用户的各设备拥有专属的 `group_device_reads` 记录，读游标与未读计数互不干扰，满足多端独立消费要求。
  - **资源回收**：
    - 所有 WebSocket 连接在测试结束时主动发送关闭帧并等待协程退出，数据库与 Redis 连接 100% 释放，无孤儿进程与句柄泄漏。

## 4. 遇到的问题与解决方案

1. **大并发 SQLite 事务升级与死锁**：
   - *问题*：20 协程并发通过 WebSocket 发送群消息时，SQLite 在默认 `DEFERRED` 模式下并发升级写锁导致 `database is locked` 报错；若全局强制指定 `_txlock=immediate`，又会阻塞其他在锁内暂停等待的测试用例（例如 `TestUploadCompletionLeaseLossKeepsCommittedMedia`）。
   - *方案*：保留标准 DSN 连接参数，在业务层 `sendGroupMessage` 与 `ackGroupMessage` 引入 `transactionWithDeadlockRetry`（指数退避与随机抖动重试），彻底消解锁争用，实现全套测试与生产环境的一致稳定。
2. **WebSocket 双向全双工帧交叉（Frame Interleaving）**：
   - *问题*：客户端在持续发送群消息等待自身 ACK 的同时，会源源不断接收来自其他 19 位成员的群广播消息。单通道顺序读取极易错把群广播识别为发送 ACK 或反之。
   - *方案*：在测试客户端内部实现 `next_of_type(expected_type, predicate)` 帧缓冲区。当等待 `ack` 时，将收到的 `group_message` 自动缓存在成员专有交付队列中，精准按 `client_id` 解耦匹配。
3. **未读游标历史测试基线对齐**：
   - *问题*：在执行离线 125 条消息回补及多设备 10 条独立未读测试时，目标用户因在前置大载荷压测中收到过多条群消息，未读计数初始值不为 0。
   - *方案*：在开始离线测试和双设备差异测试前，先驱动目标用户/设备向服务端提交当前群内最新消息的 ACK，建立确切的 0 基线，确保断言数字严格等于新增测试消息数。
4. **用户注册频控与测试性能**：
   - *问题*：公共用户注册接口 `/api/users` 设有 10 次/分钟的 IP 频控限制，连续注册 20 个用户会导致等待触发 429。
   - *方案*：在集成测试启动阶段，直接向 SQLite 数据库预批量插入 20 个已哈希密码的用户数据，并以统一密钥预签发合法 JWT，消除启动延迟与频控干扰。
