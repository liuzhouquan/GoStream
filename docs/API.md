# API reference

JSON errors use `{ "error": "..." }`; authenticated routes require `Authorization: Bearer <token>`.

`POST /api/users`, `POST /api/sessions`, and `POST /api/videos/:id/views` allow 10, 30, and 120 requests per peer IP per UTC minute respectively. All attempts count, including invalid credentials and nonexistent videos. Exceeding the budget returns HTTP 429, `{"error":"rate limit exceeded"}`, and `Retry-After` in seconds. The peer is taken from the TCP connection address; `X-Forwarded-For` and `X-Real-IP` are ignored, so a reverse proxy must apply its own trusted client-IP limits and may cause its users to share this backend budget. With `REDIS_ADDR`, API instances share one atomic Redis counter; if Redis is unavailable, each instance enforces its own bounded local counter. A fixed-window boundary can allow two budgets close together. `play_count` counts accepted requests, not unique viewers or watch completions.

`POST /api/groups/:id/members` accepts `{"user_id":123}` from the group owner. A new member beyond 200 returns HTTP 409. Repeating an invitation for an existing member returns `{"member":true}` without a second notification, even at capacity.

Registration accepts `username`, `password` (8–72 characters), and optional `nickname`; login accepts `username` and `password`. Both return a user and 24-hour access token. Passwords use bcrypt and tokens use HS256 with `JWT_SECRET`.

Single-file upload uses multipart field `file`; allowed extensions are MP4, WebM, MOV, JPEG, PNG, and WebP. The server enforces a 250 MiB limit and records the uploader. JPEG, PNG, and WebP images must fully decode after a dimensions check (at most 8192 pixels on either side and 16 million pixels total); a truncated or mismatched file returns HTTP 400 before asset registration on both direct upload and resumable completion. Video publication accepts `title`, optional `description`, `media_url`, and optional `cover_url`; the video and cover must be files uploaded by the same account. `PATCH /api/videos/:id` accepts those same editable fields and checks author ownership. Avatar updates through `PATCH /api/users/me` also require an image uploaded by that account.

When `FFMPEG_BIN` is enabled (the Compose default), `POST /api/videos` returns a video with `status: "processing"`. Only its author can read it via `GET /api/videos/:id` or see it in `GET /api/users/:id/videos`; public Feed/search/profile queries include only `published` videos. The worker uses ffprobe (`FFPROBE_BIN`, default `ffprobe`) before decoding. It rejects a missing video stream, unknown or nonpositive duration, duration over 10 minutes, a frame side over 4096 pixels, or more than 3840×2160 total pixels. Invalid source metadata marks the job and video failed on the first attempt. Accepted input is transcoded to H.264 MP4 with AAC if audio exists, and a JPEG cover is generated unless a user cover was supplied. The published video includes `duration_ms`, `width`, and `height` measured from the transcoded output. Other processing errors retry up to three attempts before `status: "failed"`. A failed video returns an author-only `processing_error` code: `invalid_media`, `missing_video`, `invalid_duration`, `duration_limit`, `resolution_limit`, or `processing_failed`. Internal worker error text is never included. The author can retry by PATCHing `media_url` to an owned upload, including the same source URL; deleting a processing or failed video is allowed. Without `FFMPEG_BIN`, publication remains immediate and these metadata fields are zero. Existing published rows from before this feature also retain zero metadata until reprocessed.

When the receiving API instance has no `FFMPEG_BIN`, a PATCH containing `media_url` for a `failed` or `processing` video returns HTTP 409 with a processing-unavailable message. The entire edit is rolled back, including any title or cover fields; the video and existing jobs keep their state. An administrator can enable FFmpeg on the serving instance and retry the same or a new owned source. Metadata-only edits remain available. Published videos can still replace their source in the no-processor mode. In a mixed configuration, an instance without FFmpeg returns 409 even if another instance has a worker.

For resumable upload, create a session with `{"filename":"clip.mp4","size":123456,"sha256":"<optional 64-character hex digest>"}`. The response returns a random `id`, `chunk_size` (4 MiB), and `expires_at`. Send bytes to `PUT /api/uploads/sessions/:id/chunks/0`, then higher indices. The final chunk may be shorter. `GET /api/uploads/sessions/:id` returns `uploaded_chunks` for retry after interruption. `POST /api/uploads/sessions/:id/complete` returns a media URL and actual SHA256; repeated completion is safe. Sessions expire after 24 hours. With `MEDIA_STORE=minio`, different API instances can accept chunks of the same session because the bucket holds private hash-qualified chunk objects and the database tracks accepted indices. MinIO outages return 503 on object operations; `/ready` remains a database-only check. Chunk bodies must match their exact expected size; a repeated index with different bytes returns 409. On the creator page, failed videos with a generic processing error offer a same-source retry; every failed video offers a replacement-file form. Both PATCH the owned video after upload and can be checked with the page's status refresh control.

Feed scenes are `timeline`, `following`, `recommend`, and `hot`; limit defaults to 10 and caps at 50. Timeline and following use descending `(created_at, id)` keyset cursors. Hot sorts by `3*likes + 5*comments + 4*favorites`, then descending video ID. Recommendation adds 12 points for age under 24 hours or 5 for age under seven days, 12 for a followed author, and 6 for an author in the viewer's recent likes/favorites. Anonymous recommendation uses interaction and age only. Recommendation cursors carry a scene and time anchor, expire after 24 hours, and should not be reused for another scene. Cursor values are opaque URL-safe base64 JSON. Responses contain `scene`, `items`, `next_cursor`, and `has_more`.

When a valid optional access token is provided, each Feed item also contains `liked` and `favorited` booleans for that viewer. Anonymous Feed requests return both as `false`.

Search accepts a trimmed 2–80-character UTF-8 `q`. `type` is `all` (default), `users`, or `videos`; `limit` defaults to 20 and can be 1–50 per result type. Results are ordered by descending ID. Pass `users_before_id` and/or `videos_before_id` from the previous response to fetch older matches without a fixed row cutoff. The response contains `users`, `videos`, `next_user_cursor`, `next_video_cursor`, `has_more_users`, and `has_more_videos`; a type-specific request returns an empty array for the other type. `%`, `_`, and `!` in `q` match literally. Only published videos appear, with their author and optional viewer-specific `liked` and `favorited` flags. Search uses substring matching and does not promise a snapshot if titles or profiles change between pages.

`POST /api/videos/:id/comments` accepts `{"body":"..."}` for a top-level comment or `{"body":"...","parent_id":123}` to reply to a top-level comment on the same published video. Bodies are trimmed and limited to 2,000 UTF-8 bytes. Replies to replies are rejected with 400. `GET /api/videos/:id/comments` returns only top-level comments; `GET /api/videos/:id/comments/:comment_id/replies` returns that root's direct replies. Both accept `limit` (default 20, maximum 50) and an opaque `cursor`; responses contain `items`, `next_cursor`, and `has_more`, ordered newest first by `(created_at, id)`. Top-level rows include `reply_count` when nonzero. A cursor belongs to one video and one comment thread; reusing it elsewhere returns 400. Listing is public, while posting requires authentication. Each comment notifies the video author unless they wrote it; a reply also notifies the parent author unless they wrote the reply or are the video author. The comment counter and notification outbox entries commit with the comment.

If `REDIS_ADDR` is configured, anonymous timeline/recommend/hot pages and each authenticated viewer's following first page use a five-second Redis cache. The following cache key includes the viewer ID and a version advanced by follow/unfollow. A successful write that changes a video card or interaction score advances the shared cache version. Authenticated non-following requests and following cursor pages read the database; Redis errors also fall back to database reads. Play counts on a cached card may lag by up to five seconds.

`GET /api/notifications` uses descending notification IDs. `limit` defaults to 30 and caps at 100; pass `next_cursor` as `before_id` for older rows. The response contains `items`, `next_cursor`, and `has_more`. `PATCH /api/notifications/read?up_to_id=<id>` marks only this account's unread rows with IDs at or below the bound and returns `read_count`. The web client uses the newest ID it received on the first page, so notifications with higher IDs stay unread. Omitting `up_to_id` preserves the earlier mark-all API. Invalid limits, cursors, and bounds return 400; database failures return 500.

WebSocket clients connect to `/api/ws` with `gostream` and `gostream.jwt.<access_token>`; device-aware clients also offer `gostream.device.<uuid>`. The browser uses all three protocols, and the server selects `gostream`. Each API instance allows up to eight simultaneous sockets per account; a ninth handshake receives 429. Clients send `{"type":"message","client_id":"<unique-per-sender>","recipient_id":2,"body":"Hi"}`, `{"type":"group_message","client_id":"<unique-per-sender>","group_id":1,"body":"Hi group"}`, or `{"type":"ping"}`. The originating socket receives an `ack` after persistence; `pong`, validation errors, and reconnect replay also go only to that socket. Committed direct/group messages are sent to every active recipient device and echoed to the sender's other devices, including devices connected to other API instances when Redis relay is enabled. Notification events use `{"type":"notification","notification":{...}}` and reach all of the user's local sockets. Direct and group messages each replay up to 100 pending rows on reconnect. `sync_required` or `group_sync_required` asks clients to page unread/history APIs for larger backlogs. With a device ID, direct-message receipts and group read cursors are independent per device. Legacy clients without a device ID retain the account-level `acked_at` and group cursor. Reusing a client ID with different content is rejected. Redis Pub/Sub delivery is best effort; clients should use unread/history APIs after reconnect. Presence falls back to process-local state if Redis is unavailable.

Direct history requires `user_id`; `limit` defaults to 50 and caps at 100. Results are ordered by descending message ID and contain `items`, `next_cursor`, and `has_more`. Pass the previous `next_cursor` as `before_id` to load older messages. The query includes only messages between the authenticated user and that peer. `POST /api/messages/acks` accepts `{"ids":[1,2]}` with 1–100 distinct incoming message IDs. It rejects the whole batch if any ID is missing or does not belong to the caller; a successful response includes `acked_count`, which is zero for an exact retry. The browser ACKs incoming messages after displaying a history page. Device-aware clients send `X-GoStream-Device-ID: <uuid>` on HTTP ACK/unread requests and the matching WebSocket device protocol. The ID is a persistent random UUID per browser profile and account; malformed IDs return 400. Direct ACKs for these clients create exact `(user, device, message)` receipts, so one device does not clear another device's pending messages. `acked_count` counts newly inserted receipts. Group ACKs advance a monotonic `(group, user, device)` cursor; a new device starts from the existing account-level group cursor, which also prevents replay before group membership. Legacy ACKs still change account-level state; a legacy direct ACK suppresses replay on all devices. `acked_at` in direct history reflects only legacy ACKs. Device-aware clients can safely ACK displayed rows again after reopening a conversation.

New device registrations are capped at 32 distinct IDs per account; upgrade backfill preserves older read state even if an account already has more IDs. A 33rd ID returns HTTP 429 when all existing IDs were used in the last 30 days; WebSocket handshakes use the same rule. If the oldest ID has been idle for more than 30 days, a new ID replaces it. An hourly worker deletes device-specific receipts and group cursors after 90 days of inactivity. A returning expired device can receive previously read messages again because its receipts were removed; unread direct messages remain in SQL. Clients should deduplicate messages by ID. Legacy clients without a device ID do not use this registry.
