# Interview preparation

## Implemented questions

1. **How do equal-timestamp Feed rows remain paginable?** Use a keyset ordered by `(created_at, id)` and carry both in the cursor. See `internal/platform/feed.go`. Interaction scores can change between recommendation pages, so those pages are not a stable snapshot.
2. **How are likes idempotent and counts kept consistent?** A unique `(user_id, video_id, kind)` row represents state. Insert/delete and the corresponding counter change happen in one transaction only when a row changed. See `social.go` and `models.go`.
3. **What closes the SQL-to-notification dual-write gap?** The notification and outbox event are inserted in the business transaction. A worker leases, retries and records dead letters. Redis can relay the committed notification ID to other instances. See `outbox.go` and `realtime.go`.
4. **When is a chat message accepted?** After message, notification and outbox commit, the sender receives ACK. A duplicate client ID with matching content returns the original message; a conflict is rejected. See `hub.go` and `messages.go`.
5. **How does a recipient recover offline messages?** A reconnect replays up to 100 unacknowledged rows; the unread API pages further rows. Recipient ACK is idempotent. See `hub.go` and `messages.go`.
6. **How do group members track unread messages?** Each member has a monotonically increasing last-acknowledged message ID. Unread counts scan later group messages excluding the user's own sends. See `groups.go` and `models.go`.
7. **How does resumable upload avoid corrupt or foreign files?** Session ownership, fixed chunk size, per-chunk hashes, full-file hash, a completion lease and an owned media record. A repeated object upload reads and hashes existing bytes; same-size corruption is repaired from the validated request body. See `uploads.go`, `uploads_object.go`, `media_store.go`, `minio_fault_test.go`, and `videos.go`.
8. **How are passwords and access tokens handled?** bcrypt hashes and HS256 JWTs; the browser offers a public WebSocket protocol and an authentication protocol, while the server negotiates only the public one. See `accounts.go`, `server.go` and `hub.go`.
9. **What happens when Redis fails or a write races with cache population?** Cached pages fall back to SQL on Redis errors. A page is stored under the version read before its SQL query; an intervening write increments the version, so later readers use a different key. Following first pages also use the viewer ID and a per-viewer follow version, so one account's follow changes do not invalidate another's cache. A failed invalidation can expose stale data until the five-second TTL expires. See `feed_cache.go`, `feed.go`, `feed_cache_test.go`, and `following_cache_test.go`.
10. **How are sockets reached on another API instance?** Redis Pub/Sub broadcasts only committed IDs; subscribers query SQL and verify recipients or group membership before sending to local sockets. Direct and group reconnect replay plus history APIs cover missed events. Pub/Sub itself is best effort. Expiring Redis entries make cross-instance presence visible. See `realtime.go`, `realtime_test.go`, and `hub.go`.
11. **How does recommendation differ from hot ranking?** Hot uses interaction counts. Recommendation adds fixed time buckets and author affinity from follows and the viewer's last 200 likes/favorites. Its cursor fixes the time anchor, while interaction and preference changes can still move items between pages. See `recommend.go`, `feed.go`, and `recommend_test.go`.
12. **How does video processing survive a crash or duplicate worker?** The video and job are created in one transaction. A conditional lease chooses one worker; an expired lease can be reclaimed, and completing a job checks the lease and original source URL. Temporary files are removed on failed commits; the video row switches to generated media URLs only after the completion transaction succeeds. See `video_processing.go`, `videos.go`, and `video_processing_test.go`.
13. **How is expensive video decoding bounded and metadata made trustworthy?** ffprobe checks the source duration and first video stream dimensions before FFmpeg runs. Invalid metadata permanently fails the job; output metadata is probed again and committed with publication. This avoids claiming input dimensions for a resized output. See `video_probe.go`, `video_processing.go`, and `video_probe_test.go`.
14. **How are failed jobs explained without exposing worker diagnostics, and how are crash orphans removed?** The job stores an internal error and a stable code. Only the author receives an allowlisted code. A periodic worker waits 24 hours, checks asset/video/unfinished-job/avatar references in batches, and deletes only matching generated regular files. Database errors stop deletion. See `videos.go`, `video_processing.go`, `media_reconcile.go`, and their tests.
15. **Why can a resumable upload pass SQLite tests but fail on MySQL?** SQLite accepted an unset `time.Time` lease as a zero date; MySQL strict mode rejected it with error 1292. The lease is now nullable and set to `NULL` when a session is open or completed. A real MySQL integration test covers the create, rollback, and completion transitions. See `models.go`, `uploads.go`, and `mysql_integration_test.go`.
16. **How are simultaneous devices handled without leaking control frames?** The hub stores a bounded set of sockets per account. Committed direct/group events are broadcast, but ACK, error, pong and replay go only to the initiating socket. Presence clears after the last local socket closes. Redis relays committed IDs so the sender's other devices on another instance also receive echoes. Direct receipts and group cursors are isolated by a persistent browser device UUID. See `device.go`, `hub.go`, `realtime.go`, `device_test.go`, and `hub_multidevice_test.go`.
17. **How is per-device state bounded without losing offline direct messages?** The registry caps new registrations at 32 IDs and serializes new registration on the user row. It can replace an ID idle for 30 days and cleans up IDs idle for 90 days. Cleanup deletes receipts and group cursors but leaves messages, so an old device can see duplicates after reconnect; clients deduplicate by message ID. A one-time backfill preserves old receipts during upgrade. See `device.go`, `models.go`, `device_test.go`, and `mysql_integration_test.go`.
18. **Why does the notification inbox pass an ID when marking read?** The first page fixes the highest ID the client has received. The read update changes only this account's older unread rows, so a higher-ID arrival stays unread. A lower-ID in-flight transaction is a documented exception. ID keyset pages and a `(user_id, id DESC)` index avoid the old fixed 50-row cutoff and equal-timestamp ambiguity. See `notifications.go`, `notifications_test.go`, `models.go`, and `web/app.js`.
19. **How can media cleanup race with video publication?** Publication, video edits, and avatar updates first lock their owned `media_assets` rows, then write references in the same transaction. The seven-day reaper locks the same row and rechecks all references before deleting its registration. Generated names, symlink checks, file identity checks, and a separate orphan pass bound file removal. Assets referenced by deleted video rows remain protected. See `videos.go`, `accounts.go`, `media_reconcile.go`, `media_reconcile_test.go`, and `mysql_integration_test.go`.
20. **How does search paginate two result types without skipping rows?** Users and published videos have separate descending-ID cursors and bounded `limit + 1` queries; a new higher-ID row cannot displace older rows on the next page. `LIKE ... ESCAPE '!'` treats `%`, `_`, and `!` literally on SQLite and MySQL. Substring search still scans text, so the next scaling step needs an index strategy and measured query plans. See `search.go`, `search_test.go`, `mysql_integration_test.go`, and `web/app.js`.
21. **How can existing local media move to MinIO without breaking URLs?** Stop writers, scan asset/video/avatar/unfinished-job SQL references and live resumable chunks, copy only generated regular files and registered chunks to the matching private object keys, compare full SHA-256 for existing and new objects, then switch the API to object mode. URLs remain `/media/<name>`. For recovery, back up SQL and the whole bucket in the same stopped-writer window; the manifest records size, hash and MIME. Restore validates all local files and destination conflicts before uploading missing objects. See `cmd/gostream-media`, `media_transfer.go`, `media_transfer_test.go`, `tests/integration/media_transfer_smoke.py`, and `docs/MEDIA_OPERATIONS.md`. This is an offline procedure, with no measured production recovery time.
22. **What if MinIO stores a transcoded output but its success response is lost?** The worker registers best-effort cleanup before its first output PUT, so either the video or cover upload can fail after committing an object without publishing a missing or unregistered asset. SQL completion still checks the job lease and source URL; a later attempt uses new output names. The orphan reaper covers deletion failures during a storage outage. `minio_processing_fault_test.go` injects lost responses after real MinIO commits both output types and verifies a third-attempt recovery. Image uploads first check dimensions and then decode all JPEG/PNG/WebP bytes, so a valid signature alone cannot register a truncated image. See `video_processing.go`, `videos.go`, and `image_validation_test.go`. The fault fixture isolates output storage and does not run FFmpeg itself.
23. **How does the following Feed combine push and pull without losing posts during fanout?** Publication creates a job in the same transaction as the public video state. Until a job is complete, the pull branch includes that video; afterward, the inbox branch includes preexisting followers. High-follower and legacy videos stay on pull, while late follows pull historical posts. Both branches cap candidates at one page, merge by `(created_at, id)`, and deduplicate. The worker checkpoints a follower ID and uses a unique inbox pair so retries cannot multiply rows. See `feed_fanout.go`, `following_feed.go`, `feed.go`, `feed_fanout_test.go`, and `docs/FEED_HYBRID.md`. The 2,000-user MySQL comparison showed a read regression for one low-follow-count viewer, so the threshold now defaults to zero; explain this measured limit and the extra pull-branch cost instead of claiming a performance gain.

24. **Why use both publisher confirms and consumer ACKs?** A source outbox row is complete only after a persistent mandatory publication is routed and confirmed. This proves broker acceptance, not consumption. The consumer first commits a unique `broker-delivery:<source-key>` SQL outbox row and then ACKs. Lost source completion or a lost consumer ACK repeats the same stable event key. Two MySQL-backed consumers processing sixteen copies produced one delivery job. See `rabbitmq.go`, `broker_events.go`, and `rabbitmq_integration_test.go`. A delivery worker can still repeat a WebSocket hint after lease loss, so durable idempotency does not imply exactly-once screen notifications.
25. **How do failures reach a replayable dead letter?** RabbitMQ 4.3 quorum queues use failed-delivery delay and a delivery limit; transient SQL failures call `Reject(true)`, because `basic.nack` does not advance that failed-delivery counter in this version. Invalid envelopes call `Reject(false)`. The durable DLQ has a bound route before the source queue is declared, with at-least-once dead lettering. `gostream-events -dead-letters N` confirms republishing before acknowledging each DLQ entry; `-outbox-key KEY` only resets one dead unpublished SQL row. See `event_replay.go`, `cmd/gostream-events`, and `docs/RABBITMQ.md`. A one-node broker restart was tested; multi-node failover, unavailable DLQ targets and actual process kills at all commit boundaries remain acceptance work.
