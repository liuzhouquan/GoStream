# Database design

The first schema is defined by GORM models in `internal/platform/models.go` and migrated at startup. The local profile uses a persistent SQLite file; the container profile uses MySQL. Production deployment should use versioned SQL migrations before schema changes become operationally sensitive.

Implemented tables: `users`, `media_assets`, `upload_sessions`, `upload_chunks`, `videos`, `follows`, `video_actions`, `comments`, `notifications`, `chat_messages`, `chat_groups`, `group_members`, `group_messages`, `group_reads`, and `outbox_events`. Direct chats use sender/recipient pairs; groups use membership and per-user read cursors. Important uniqueness constraints include username, media URL, `(upload_session_id, index)`, `(follower_id, followee_id)`, `(user_id, video_id, kind)`, `(user_id, event_key)`, `(sender_id, client_id)`, group membership, group read cursor, `(sender_id, client_id)` for group messages, and outbox event key. Feed access uses indexes on status/creation time and author/creation time; comments, notifications, relationships, and unread messages have supporting indexes.

`media_assets` binds each uploaded URL to an owner, type and size. `upload_sessions` carries the expected size/hash, 24-hour expiry and completion lease; `upload_chunks` records per-chunk size and hash. The chunk files are stored outside the public media root. `outbox_events` is a database queue with attempt count, next availability, completion time and dead-letter time. A worker claims ready rows with a conditional update and dispatches notification events. GORM auto-migration is convenient for local learning; versioned migrations, rollback practice and MySQL query-plan validation remain future work.
