# Database design

The first schema is frozen in `internal/migrations/sql/v001_sqlite.sql`, `v001_mysql.sql`, `v001_mysql_indexes.sql`, and `v001_columns.json`. `schema_v002` adds the outbox dispatch index; `schema_v003` adds durable Feed fanout jobs and inboxes; `schema_v004` adds the indexed `videos.feed_pull` flag and backfills completed jobs. `schema_v005` adds lossless per-device ACK ranges. `internal/migrations` records all five versions in `schema_migrations`; normal restarts skip completed versions. `internal/platform/models.go` remains the application model, and `platform.MigrateSchema` is retained for legacy/test fixtures and schema comparison, not production startup. The local profile uses a persistent SQLite file with WAL, a five-second busy timeout, and foreign-key enforcement; the container profile uses MySQL. The SQLite settings use driver-supported `_journal_mode`, `_busy_timeout`, and `_foreign_keys` DSN options, and `cmd/gostream/main_test.go` checks their effective PRAGMA values. An isolated MySQL backup/restore and v002 rollback drill is available; broader schema drift checks and full application disaster recovery remain.

Implemented tables: `users`, `media_assets`, `upload_sessions`, `upload_chunks`, `videos`, `video_process_jobs`, `follows`, `feed_fanout_jobs`, `feed_inboxes`, `video_actions`, `comments`, `notifications`, `chat_messages`, `message_device_acks`, `message_device_ack_ranges`, `message_devices`, `chat_groups`, `group_members`, `group_messages`, `group_reads`, `group_device_reads`, `outbox_events`, and `schema_migrations`. Direct chats use sender/recipient pairs; groups use membership and per-user read cursors. Important uniqueness constraints include username, media URL, `(upload_session_id, index)`, `(follower_id, followee_id)`, `(user_id, video_id, kind)`, `(user_id, event_key)`, `(sender_id, client_id)`, `(user_id, device_id)` for registered message devices, group membership, group read cursor, `(sender_id, client_id)` for group messages, and outbox event key. Feed access uses indexes on status/creation time and author/creation time; comments, notifications, relationships, and unread messages have supporting indexes.

`media_assets` binds each uploaded URL to an owner, type and size. Its creation-time index supports seven-day registered-media cleanup; indexes on video media/cover URLs, user avatar URLs, and processing-job source URLs support reference checks. Publication, video edits, and avatar changes lock the asset registration before storing a reference; cleanup takes the same row lock and rechecks references before deleting it. `upload_sessions` carries the expected size/hash, 24-hour expiry and a nullable completion lease. The lease is `NULL` for open and completed sessions; an incomplete completion restores the session to open and clears the lease. This avoids invalid zero dates under MySQL strict mode. `upload_chunks` records per-chunk size and hash. In local mode chunks are stored outside the public media root. In MinIO mode chunks use hash-qualified `chunks/<session>/<index>/<sha256>` keys in a private bucket, while MySQL selects the accepted hash via the unique session/index row. The object key is derived from immutable session and chunk data; the database stores logical media URLs, not deployment-specific bucket names. The final media asset and completed session state commit in one transaction after object upload. An object uploaded before a failed transaction becomes an orphan and is eligible for later reconciliation. `outbox_events` is a database queue with attempt count, next availability, completion time and dead-letter time. A worker claims ready rows with a conditional update and dispatches notification events. MySQL query-plan validation remains future work.

Upload completion renews its five-minute `lease_until` every 100 seconds with a conditional update matching the previous deadline. The heartbeat stops before finalization; the asset/session transaction requires that latest deadline and an unexpired lease. Cleanup atomically moves eligible expired sessions to `cleaning` before removing bytes. That state also carries a five-minute lease, allowing another cleanup pass to recover an interrupted cleanup after expiry. It never returns to `open`; completed sessions remain for idempotent completion retries. These states use the existing status/deadline columns and require no schema migration.

In broker mode `outbox_events` has two topics: `notification.created` becomes published only after RabbitMQ confirms routing, and `notification.deliver` is a durable consumer effect keyed by `broker-delivery:<source-key>`. Inserting this unique row and acknowledging afterward makes duplicate consumption idempotent without another schema. Source and delivery rows have separate attempts/dead states; keep their keys for the entire replay horizon. `cmd/gostream-events` explicitly requeues dead unpublished rows or confirms DLQ republish before ACK.

## Current migration baseline

`feed_fanout_jobs.video_id` is unique so publication cannot queue a video twice; `(done_at, available_at, lease_until, id)` supports pending-job claims. `feed_inboxes` has unique `(user_id, video_id)` for replay safety and `(user_id, created_at DESC, video_id DESC)` for a viewer's inbox page. The read path also checks the current follow relation and video status. Job and inbox retention/compaction are not implemented yet. See [the hybrid Feed design](FEED_HYBRID.md).

On an empty database, `migrations.Apply` creates the migration registry from frozen DDL, runs the ordered v001 table/index statements, validates required v001 columns, and records v001. It then creates `idx_outbox_dispatch (published_at, dead_at, available_at, id)` and records v002. That index targets the outbox worker's pending/deadline predicate; no measured speedup is claimed. V003 creates Feed job/inbox tables, unique constraints, and dispatch/paging indexes; it checks required columns and index shape before recording its marker. SQLite uses `IF NOT EXISTS` for tables and indexes. MySQL table DDL contains the original indexes and foreign keys; a separate frozen index list restores missing indexes when adopting a prior AutoMigrate database. Existing user/outbox rows and the separate `message_devices_v1` backfill marker remain intact. If interrupted before a version marker is written, a later boot retries. MySQL starts take a named `GET_LOCK` so two API instances do not migrate at the same time. An older binary refuses an unknown `schema_v*` marker.

MySQL DDL is not transactional. **Do not edit a model and assume marked databases will upgrade.** Future schema changes need new numbered migrations; do not regenerate or edit the frozen SQL. The column manifest detects missing v001 columns when an unmarked legacy database is adopted, but does not validate column types or existing v001 index definitions with the same names. Such incompatible legacy schemas require a deliberate upgrade instead of silent adoption. Back up data before manual recovery from failed MySQL DDL. The v004 backfill updates completed-job videos and can be retried after an interrupted index build; plan an upgrade window and measure lock duration on larger databases. For the tested v002 reversal in a disposable restore, stop writers, remove v005, v004 and v003 markers first, remove `idx_outbox_dispatch`, then remove the v002 marker; rerunning `Apply` replays v002–v005 without dropping Feed data. Restore a tested backup for broader rollback. This procedure does not prove a live downgrade is safe.

Migration tests require disposable empty databases. `GOSTREAM_TEST_MYSQL_DSN` runs the fresh-schema/concurrent-start test; `GOSTREAM_TEST_MYSQL_LEGACY_DSN` runs the existing-schema adoption test in a second database. The legacy test starts with user data and a device backfill marker, removes the Feed index to model an interrupted baseline, then verifies that `Apply` restores it, preserves data and markers, and is safe to repeat. A following test removes the v005, v004, v003 and v002 markers, replays all upgrades, and checks an existing outbox row. A metadata comparison checks columns, indexes, and foreign keys between the frozen SQL and legacy GORM paths. SQLite tests compare v001 table/index DDL with current models after accounting for later additions, force a real index-creation failure before the marker, reject an incomplete legacy table, retry blocked v002/v003 upgrades, backfill v004 and reject a non-unique v003 inbox index. CI runs those checks before the platform's `TestMySQL*` tests. Neither DSN should point at the demo database.

## MySQL backup and recovery drill

With the Compose MySQL container running, execute the following from the repository root using the exact Go version in `go.mod`:

```sh
GOSTREAM_GO_BIN=/usr/local/go/bin/go \
GOSTREAM_RECOVERY_DSN_PREFIX='gostream:gostream-local@tcp(127.0.0.1:3307)/' \
bash tests/integration/mysql_recovery.sh "$(docker compose ps -q mysql)"
```

The script creates two randomly named databases and grants the application user access to those temporary databases. It applies production migrations to the source, inserts a user, related video, and outbox row, and takes a `mysqldump --single-transaction` snapshot. It imports the dump into the second database and checks all five version markers, linked rows, event payload, and the four-column v002 index. It then removes the v005/v004/v003 markers and v002 index/marker, verifies the v002 state, runs `migrations.Apply` twice, and verifies the original rows and rebuilt index. It prints the dump SHA-256, removes the temporary dump and both databases, and revokes their grants even when an assertion fails. CI runs the same script against its MySQL 8.4 service.

This is a logical MySQL database drill on a quiescent fixture. It does not back up media files, Redis, or an actively written production database, and it does not measure recovery time or recovery point. A full deployment backup must include the media volume or object store under the same stopped-writer window as the SQL snapshot. `cmd/gostream-media` and `docs/MEDIA_OPERATIONS.md` provide object backup/restore; the isolated integration script has restored a MySQL dump and MinIO media into a separate database and bucket. Online backup consistency, retention policy and production recovery time remain unmeasured. Do not point the drill at a real application database.

`video_process_jobs` is a second durable queue. A job records the video/source URL, next attempt time, conditional lease, attempts, completion/dead-letter timestamps, internal last error, and a stable failure code. Only the allowlisted code is exposed to the author of a failed video. A source URL change supersedes an older job; the worker checks the current video before publishing outputs. The `videos` row stores `duration_ms`, `width`, and `height` from the transcoded file in the same transaction that publishes the video. New processing resets these fields to zero first; legacy and non-transcoded rows also have zero values. The `(status, created_at DESC)` video index keeps processing/failed rows out of public Feed queries.

Notification inbox pages use `(user_id, id DESC)` and a strict `id < before_id` keyset cursor. An additional `(user_id, read_at, id DESC)` index supports unread counts and bounded read updates. The update filters on the owner, unread state, and `id <= up_to_id`, so notifications assigned higher IDs after the page was fetched remain unread. The older `(user_id, created_at DESC)` index remains on existing databases until a versioned migration can remove it after query-plan review.

Direct history pages use `chat_messages.id` as a keyset cursor and `(sender_id, recipient_id, id DESC)` for each direction of a conversation. A second `(recipient_id, acked_at)` index supports the unread query. A legacy recipient ACK updates only their unacknowledged rows. With a device ID, the unique `(user_id, device_id, message_id)` receipt table records exact displayed messages; unread and replay queries exclude both these rows and the same device’s lossless adjacent-ID ranges. The range table is unique on `(user_id, device_id, first_message_id)` and stores inclusive first/last bounds; unacknowledged numeric gaps remain outside every range. A legacy global `acked_at` still suppresses device replay. Group device cursors have a unique `(group_id, user_id, device_id)` key, advance monotonically, and fall back to the account-level join/read baseline until that device first ACKs. The batch ACK checks ownership of every requested ID before changing any row and is idempotent on retries. The older `(sender_id, recipient_id, created_at)` index remains on existing databases; a future versioned migration can remove it after query-plan review.

Unread/replay uses `direct_unread.go`: a read-only repeatable-read transaction scans bounded ordered candidate/interval pages with constant key bounds, preserving the same snapshot across every batch. Sparse global-ACK gaps cannot bypass unknown intervals. The unchanged v005 index supports predecessor and forward seeks; see [query measurements and limits](DEVICE_ACK_QUERY.md).

`message_devices` has a unique `(user_id, device_id)` key and an indexed inactivity clock. New device registration serializes on the user row, enforcing a 32-ID cap on new registrations; upgrade backfill preserves any existing excess IDs. When full, the oldest ID can be evicted after 30 days without activity; a worker removes IDs idle for 90 days in bounded batches. Eviction and expiry transactionally delete that device's direct receipts and group cursors. Chat messages remain, so an expired device can replay previously read direct messages but does not lose pending direct messages. `schema_migrations` records a one-time backfill of preexisting receipt/cursor owners on upgrade. ACK transactions now hold the same user lock while merging consecutive explicit IDs into device-specific ranges. Eviction/expiry also removes those ranges. Sparse IDs and older untouched receipts can still grow; see [compaction and upgrade limits](DEVICE_ACK_RANGES.md).

Recommendation uses the newest 200 likes/favorites per viewer to derive interacted authors. The `(user_id, id DESC)` index on `video_actions` supports this bounded lookup. It also checks the `(follower_id, followee_id)` unique index on `follows`. The computed recommendation score currently sorts matching published videos at read time; MySQL query-plan and larger-corpus measurements remain.

Comments have one level of replies through nullable `parent_id`. The `(video_id, parent_id, created_at DESC, id DESC)` index supports both root and reply keyset pages, including equal timestamps. Reply counts are grouped over the roots in the requested page, rather than queried once per row or maintained as a second counter. The video `comment_count` includes roots and replies; a transaction increments it when creating a comment. Replies create an additional outbox-backed notification for the parent author when that user differs from the commenter and video author.


## v005 device receipt upgrade

V005 creates `message_device_ack_ranges` without rewriting messages, legacy `acked_at` or existing exact receipts. It checks required columns and the unique owner/device/start index before recording `schema_v005`, and can retry missing-index creation. Stop all old API writers and take a SQL backup before upgrading; an older running binary does not understand the compressed representation. A downgrade must first expand every range into exact receipts or restore a pre-v005 backup. Dropping the range table or just deleting its marker would restore old unread messages. The disposable v002 recovery drill removes later markers only to reapply current migrations; it is not a safe old-binary downgrade procedure.
