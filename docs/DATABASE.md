# Database design

The first schema is defined by GORM models in `internal/platform/models.go`. `internal/migrations` now applies a one-time `schema_v001` baseline and records it in `schema_migrations`; normal restarts skip the baseline. The local profile uses a persistent SQLite file with WAL, a five-second busy timeout, and foreign-key enforcement; the container profile uses MySQL. The SQLite settings use the driver-supported `_journal_mode`, `_busy_timeout`, and `_foreign_keys` DSN options, and `cmd/gostream/main_test.go` checks their effective PRAGMA values. The baseline still uses GORM `AutoMigrate`, so frozen SQL files, explicit upgrades, rollback/recovery practice, and drift checks remain before the A10 release gate can pass.

Implemented tables: `users`, `media_assets`, `upload_sessions`, `upload_chunks`, `videos`, `video_process_jobs`, `follows`, `video_actions`, `comments`, `notifications`, `chat_messages`, `message_device_acks`, `message_devices`, `chat_groups`, `group_members`, `group_messages`, `group_reads`, `group_device_reads`, `outbox_events`, and `schema_migrations`. Direct chats use sender/recipient pairs; groups use membership and per-user read cursors. Important uniqueness constraints include username, media URL, `(upload_session_id, index)`, `(follower_id, followee_id)`, `(user_id, video_id, kind)`, `(user_id, event_key)`, `(sender_id, client_id)`, `(user_id, device_id)` for registered message devices, group membership, group read cursor, `(sender_id, client_id)` for group messages, and outbox event key. Feed access uses indexes on status/creation time and author/creation time; comments, notifications, relationships, and unread messages have supporting indexes.

`media_assets` binds each uploaded URL to an owner, type and size. Its creation-time index supports seven-day registered-media cleanup; indexes on video media/cover URLs, user avatar URLs, and processing-job source URLs support reference checks. Publication, video edits, and avatar changes lock the asset registration before storing a reference; cleanup takes the same row lock and rechecks references before deleting it. `upload_sessions` carries the expected size/hash, 24-hour expiry and a nullable completion lease. The lease is `NULL` for open and completed sessions; an incomplete completion restores the session to open and clears the lease. This avoids invalid zero dates under MySQL strict mode. `upload_chunks` records per-chunk size and hash. The chunk files are stored outside the public media root. `outbox_events` is a database queue with attempt count, next availability, completion time and dead-letter time. A worker claims ready rows with a conditional update and dispatches notification events. MySQL query-plan validation remains future work.

## Current migration baseline

On an empty database, `migrations.Apply` creates the migration registry, runs the additive GORM schema baseline, then writes `schema_v001`. On a database previously managed by startup `AutoMigrate`, the same additive baseline runs once and preserves existing rows; the separate `message_devices_v1` backfill marker remains intact. If interrupted before the marker is written, a later boot retries. MySQL starts take a named `GET_LOCK` during this step so two API instances do not migrate at the same time. An older binary refuses an unknown `schema_v*` marker.

MySQL DDL is not transactional, and `schema_v001` still reads the current model definitions. **Do not edit a model and assume the baseline will upgrade an already marked database.** Before the next schema change, freeze the v001 schema and add an explicit v002 migration with an upgrade test. Back up data before a manual recovery from a failed MySQL DDL operation. Rollback is not yet implemented; this is partial progress toward A10, not a claim of completed release-grade migration support.

Migration tests require disposable empty databases. `GOSTREAM_TEST_MYSQL_DSN` runs the fresh-schema/concurrent-start test; `GOSTREAM_TEST_MYSQL_LEGACY_DSN` runs the existing-schema adoption test. The former creates tables and is also used by the CI MySQL job before the platform's `TestMySQL*` tests. Neither variable should point at the demo database.

`video_process_jobs` is a second durable queue. A job records the video/source URL, next attempt time, conditional lease, attempts, completion/dead-letter timestamps, internal last error, and a stable failure code. Only the allowlisted code is exposed to the author of a failed video. A source URL change supersedes an older job; the worker checks the current video before publishing outputs. The `videos` row stores `duration_ms`, `width`, and `height` from the transcoded file in the same transaction that publishes the video. New processing resets these fields to zero first; legacy and non-transcoded rows also have zero values. The `(status, created_at DESC)` video index keeps processing/failed rows out of public Feed queries.

Notification inbox pages use `(user_id, id DESC)` and a strict `id < before_id` keyset cursor. An additional `(user_id, read_at, id DESC)` index supports unread counts and bounded read updates. The update filters on the owner, unread state, and `id <= up_to_id`, so notifications assigned higher IDs after the page was fetched remain unread. The older `(user_id, created_at DESC)` index remains on existing databases until a versioned migration can remove it after query-plan review.

Direct history pages use `chat_messages.id` as a keyset cursor and `(sender_id, recipient_id, id DESC)` for each direction of a conversation. A second `(recipient_id, acked_at)` index supports the unread query. A legacy recipient ACK updates only their unacknowledged rows. With a device ID, the unique `(user_id, device_id, message_id)` receipt table records exact displayed messages; unread and replay queries anti-join it. A legacy global `acked_at` still suppresses device replay. Group device cursors have a unique `(group_id, user_id, device_id)` key, advance monotonically, and fall back to the account-level join/read baseline until that device first ACKs. The batch ACK checks ownership of every requested ID before changing any row and is idempotent on retries. The older `(sender_id, recipient_id, created_at)` index remains on existing databases; a future versioned migration can remove it after query-plan review.

`message_devices` has a unique `(user_id, device_id)` key and an indexed inactivity clock. New device registration serializes on the user row, enforcing a 32-ID cap on new registrations; upgrade backfill preserves any existing excess IDs. When full, the oldest ID can be evicted after 30 days without activity; a worker removes IDs idle for 90 days in bounded batches. Eviction and expiry transactionally delete that device's direct receipts and group cursors. Chat messages remain, so an expired device can replay previously read direct messages but does not lose pending direct messages. `schema_migrations` records a one-time backfill of preexisting receipt/cursor owners on upgrade. Exact receipts for devices that remain active continue to grow with acknowledged messages; safe compaction remains future work.

Recommendation uses the newest 200 likes/favorites per viewer to derive interacted authors. The `(user_id, id DESC)` index on `video_actions` supports this bounded lookup. It also checks the `(follower_id, followee_id)` unique index on `follows`. The computed recommendation score currently sorts matching published videos at read time; MySQL query-plan and larger-corpus measurements remain.

Comments have one level of replies through nullable `parent_id`. The `(video_id, parent_id, created_at DESC, id DESC)` index supports both root and reply keyset pages, including equal timestamps. Reply counts are grouped over the roots in the requested page, rather than queried once per row or maintained as a second counter. The video `comment_count` includes roots and replies; a transaction increments it when creating a comment. Replies create an additional outbox-backed notification for the parent author when that user differs from the commenter and video author.
