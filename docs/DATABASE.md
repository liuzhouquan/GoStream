# Database design

The first schema is defined by GORM models in `internal/platform/models.go` and migrated at startup. The local profile uses a persistent SQLite file; the container profile uses MySQL. Production deployment should use versioned SQL migrations before schema changes become operationally sensitive.

Implemented tables: `users`, `media_assets`, `upload_sessions`, `upload_chunks`, `videos`, `video_process_jobs`, `follows`, `video_actions`, `comments`, `notifications`, `chat_messages`, `chat_groups`, `group_members`, `group_messages`, `group_reads`, and `outbox_events`. Direct chats use sender/recipient pairs; groups use membership and per-user read cursors. Important uniqueness constraints include username, media URL, `(upload_session_id, index)`, `(follower_id, followee_id)`, `(user_id, video_id, kind)`, `(user_id, event_key)`, `(sender_id, client_id)`, group membership, group read cursor, `(sender_id, client_id)` for group messages, and outbox event key. Feed access uses indexes on status/creation time and author/creation time; comments, notifications, relationships, and unread messages have supporting indexes.

`media_assets` binds each uploaded URL to an owner, type and size. `upload_sessions` carries the expected size/hash, 24-hour expiry and completion lease; `upload_chunks` records per-chunk size and hash. The chunk files are stored outside the public media root. `outbox_events` is a database queue with attempt count, next availability, completion time and dead-letter time. A worker claims ready rows with a conditional update and dispatches notification events. GORM auto-migration is convenient for local learning; versioned migrations, rollback practice and MySQL query-plan validation remain future work.

`video_process_jobs` is a second durable queue. A job records the video/source URL, next attempt time, conditional lease, attempts, completion/dead-letter timestamps and last error. A source URL change supersedes an older job; the worker checks the current video before publishing outputs. The `videos` row stores `duration_ms`, `width`, and `height` from the transcoded file in the same transaction that publishes the video. New processing resets these fields to zero first; legacy and non-transcoded rows also have zero values. The `(status, created_at DESC)` video index keeps processing/failed rows out of public Feed queries.

Recommendation uses the newest 200 likes/favorites per viewer to derive interacted authors. The `(user_id, id DESC)` index on `video_actions` supports this bounded lookup. It also checks the `(follower_id, followee_id)` unique index on `follows`. The computed recommendation score currently sorts matching published videos at read time; MySQL query-plan and larger-corpus measurements remain.
