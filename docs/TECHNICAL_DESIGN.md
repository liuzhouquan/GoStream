# Technical design notes

These notes distinguish current behavior from the next implementation step. They are updated with source changes.

## Feed pagination and ranking

`internal/platform/feed.go` implements timeline and following feeds ordered by `created_at DESC, id DESC`; the opaque cursor carries both values so equal timestamps do not skip or duplicate a row. Feed requests fetch `limit + 1` rows to determine `has_more`. Hot ranks by `3*likes + 5*comments + 4*favorites`, tie-broken by ID. Recommendation starts with that same interaction score, adds 12 points for a video younger than 24 hours or 5 for one younger than seven days, 12 for a followed author, and 6 for an author found among the viewer's 200 most recent likes/favorites. Anonymous viewers receive the interaction and freshness parts. `recommend.go` computes the SQL ordering and the cursor score from the same weights. The recommendation cursor includes a fixed time anchor and scene, expires after 24 hours, and avoids recency buckets changing between pages. Interaction counts and preferences can still change between requests, so score-based pagination is not a stable snapshot. The strategy favors known authors and has no topic model or author-diversity control.

Following Feed can use bounded push plus pull. At publication, a video with no more than `FEED_FANOUT_MAX_FOLLOWERS` followers gets a durable fanout job; higher-follower authors remain on the video/follow join. The worker fills follower inboxes in idempotent batches. Read queries merge inbox candidates with high-follower, unfinished-job, legacy, and late-follow candidates, then deduplicate by video ID. The per-viewer first-page Redis cache remains; cursor pages read SQL. The threshold defaults to zero, retaining the SQL-only path, because the measured 2,000-user fixture showed a hybrid read regression; set it explicitly to exercise the hybrid path. The exact invariants, retry behavior, migration, and current limitations are in [`FEED_HYBRID.md`](FEED_HYBRID.md), with measured results in [`PERFORMANCE.md`](PERFORMANCE.md).

## Interaction state

`video_actions` has a unique constraint on `(user_id, video_id, kind)`. A like/favorite transition and its denormalized video count are updated in one database transaction. The insert uses `ON CONFLICT DO NOTHING`; the count changes only when a row was inserted or removed. Repeating PUT does not increment twice, and repeating DELETE does not decrement twice. Notifications have a unique `(user_id, event_key)` constraint so retries do not create duplicate notices.

Counts are maintained synchronously in the same database. A notification and an outbox event are written in the same transaction as a new interaction or comment. The outbox worker leases rows for 30 seconds, retries failed sends with exponential delay, and marks an event dead after eight attempts. The database inbox is authoritative; local WebSocket push is a convenience. The optional Redis page cache is invalidated by advancing a version after successful interaction writes; Redis does not own counters.

The notification inbox uses descending ID keyset pages with a `(user_id, id DESC)` index, a `limit + 1` query, and a maximum page size of 100. The web client loads older pages on demand. When the user marks notifications read, it sends the newest ID from its first page; the update affects only unread rows for that account up to that ID. Notifications with higher IDs remain unread. An older in-flight transaction can still commit a lower ID after the page load; this bound is not a cross-request database snapshot. An omitted bound keeps the older mark-all API. Database errors produce server errors instead of successful empty responses.

Comment threads are one level deep. Root and reply listings use separate `(created_at DESC, id DESC)` keyset pages with a cursor bound to the video and root comment. The API queries `limit + 1` rows and batches reply counts for the visible root IDs. A reply checks that its parent belongs to the same published video, then commits the comment, video counter, and any author/parent notifications in one transaction. The UI loads replies on demand, supports pagination in each thread, and refreshes the relevant page after posting.

## Messaging semantics

The WebSocket hub in `internal/platform/hub.go` is process-local and keeps up to eight connections per account on each instance. Each connection has its own write mutex; the hub snapshots recipients under a read lock, then writes outside the registry lock. A direct message, notification, and outbox event commit together before the originating socket receives an ACK; a group message commits before its ACK. ACK, error, pong, and replay frames stay on that socket; committed direct and group messages reach every active recipient device and are echoed to the sender's other devices. `(sender_id, client_id)` makes exact retries resolve to the same stored message; reusing an ID with different content is rejected. A recipient reconnect replays up to 100 unacknowledged messages; `GET /api/messages/unread` pages through the rest. Direct conversation history uses descending message-ID keyset pages, so new messages do not shift older pages. The web client loads older pages on demand and batch-ACKs the incoming rows it displayed; the batch rejects foreign IDs before updating any row. A valid device UUID in the HTTP header and WebSocket subprotocol selects device-specific read state. Direct ACKs insert exact unique receipts per `(user, device, message)`, leaving other devices' pending rows intact; unread paging and reconnect replay anti-join those receipts. Group ACKs atomically advance a unique `(group, user, device)` cursor; the account-level group cursor is the baseline before that device has ACKed and after a member is added. Membership removal deletes its device cursors. Clients without a device ID continue to use the legacy account-level `acked_at` and group cursor. Legacy direct ACKs also suppress device replay for compatibility. The browser stores one random device UUID per account in localStorage. A SQL registry bounds each account to 32 device IDs. New registrations lock the user row to serialize the count across instances; active device lookups refresh last-seen time at most once per minute. When full, a device idle for 30 days can be replaced. An hourly worker deletes devices idle for 90 days and their direct receipts/group cursors in one transaction; old read messages may replay, but pending direct messages stay in SQL. A one-time startup backfill preserves receipts and cursors from before the registry was added. Exact receipts for continuously active devices are not compacted yet.

Groups have an owner, a unique membership row for each user, durable messages, and a per-member monotonically increasing read cursor. Members can read history and send; only owners can invite or remove others. Local group fanout uses the same hub; with `REDIS_ADDR`, a Pub/Sub event causes each other API instance to query current membership and deliver to its local sockets, including other devices of the sender. Direct-message and outbox-notification events are relayed similarly, using committed database IDs rather than payload content. A direct relay does not suppress an event merely because another device already ACKed the message; active devices still receive the committed event. Redis subscription reconnects after interruption. Direct and group publication is best effort, so Pub/Sub outages can delay online delivery; SQL unread/history APIs recover missed data. Outbox notification publication retries failures. On reconnect, each socket receives up to 100 unacknowledged group messages in ID order, followed by `group_sync_required` when more exist; the client can then read group history. Local presence comes from active connections; with Redis, each instance refreshes an expiring per-user/per-node sorted-set entry every 30 seconds, and other instances count unexpired entries. Only the last local disconnect removes the node's presence entry and persists `last_seen_at`; that database write now retries a few times after transient locking errors and logs a permanent failure. A crashed node ages out within 75 seconds. Without Redis or during Redis failure, only local presence is visible. The browser offers `gostream`, `gostream.jwt.<token>`, and `gostream.device.<uuid>` WebSocket subprotocols; the server negotiates only the public `gostream` protocol and reads the other two for authentication and read-state selection. The API logger records paths without query parameters. Clients should deduplicate deliveries by message ID.

## Search

Search is implemented in `search.go`. It validates the query by Unicode character count, escapes user-entered LIKE wildcards with an explicit `!` escape character, and uses descending ID keyset pages. User and video cursors are independent so the web client can request more of one type without paging the other. The limit is at most 50 rows per type; video results include only published rows, preload their author, and batch-load the current viewer's like/favorite state. This is a deliberate substring-search baseline for a small catalog. Because the pattern begins with `%`, ordinary B-tree indexes cannot accelerate the text match; larger datasets will need an appropriate full-text or external search index and measured query plans.

## Media upload

The authenticated single-file upload handler accepts a 250 MiB request cap. In local mode it writes to disk under a random name; in object mode it validates a temporary file and uploads it into a private MinIO bucket before registering the asset. A separate resumable flow creates a session, accepts 4 MiB chunks in any order, stores per-chunk SHA256 values, then assembles and hashes the full file. A database completion lease limits concurrent finalization. In local mode, incomplete chunks live beside the public media directory in `MEDIA_DIR.chunks`. In object mode, each chunk uses a hash-qualified `chunks/<session>/<index>/<sha256>` key so competing API instances cannot overwrite each other; the unique SQL chunk row chooses the accepted hash. On a retry, an existing object is read and checked against the chunk SHA-256 even when its size matches; mismatched or missing bytes are replaced using the validated request body before returning success. This adds an object read on repeat uploads, while first writes still use the normal single PUT. Incomplete sessions expire after 24 hours and the cleanup worker removes their chunks. Completion assembles into a private temporary file, verifies each chunk and the full SHA256, uploads the final object, and atomically commits the asset and session status under a conditional lease. A repeated completion returns the same URL. Published video and cover URLs must belong to the current account. MP4/MOV/WebM signatures are checked. JPEG, PNG, and WebP image uploads require a dimensions preflight (at most 8192 pixels on either side and 16 million pixels total) followed by a full decode; WebP also requires its RIFF length to match the uploaded file. This rejects truncated images on direct and resumable completion paths.

When `FFMPEG_BIN` is set, publication and a `video_process_jobs` row commit together, with the video initially hidden as `processing`. The worker conditionally claims a five-minute database lease and handles one job at a time per instance. Before decoding, ffprobe reads the first video stream and duration with a 15-second timeout. Missing/invalid metadata, duration over 10 minutes, a side over 4096 pixels, or more than 3840×2160 pixels total permanently fails the job after one attempt. These checks apply to reported stream metadata and do not inspect every frame for later resolution changes. The four-minute FFmpeg command timeout and two encoder threads bound processing. The worker produces H.264 MP4 (AAC when the source has audio) plus a JPEG cover in a private temporary directory. It probes the output and stores its duration, width, and height with the media asset records and published video in one transaction. Output cleanup is registered before the first MinIO PUT, because an object can commit even when its success response is lost. A failed video or cover PUT, failed transaction, or replaced/deleted source triggers immediate best-effort removal of both generated objects; the orphan reaper handles cleanup that cannot complete while storage is unavailable. An expired lease is reclaimable after a crash. Other failures retry up to three attempts with a growing delay, then mark the video `failed`; an author can resubmit the source. The job stores internal error text but the author API returns only an allowlisted failure code, which the creator page renders as a short reason. Temporary processing directories older than 24 hours are cleaned periodically. An hourly reconciliation also checks generated files in `MEDIA_DIR` after a 24-hour grace period; in batches of 100 it retains files referenced by assets, videos (including deleted rows), unfinished processing jobs, or avatars and deletes unreferenced regular files. It skips symlinks, unexpected names, and recently modified files. Database failures stop deletion. A second pass pages through registered assets created more than seven days ago and removes those without a video, avatar, or unfinished-job reference. It accepts only generated filenames and regular files older than the cutoff; missing files lose their stale registration, while changed files are left for the unregistered-file pass. Publication, edits, and avatar updates lock the selected asset row and commit their reference in the same transaction. The reaper locks that row and rechecks all references before deleting it; a new reference either commits first and protects the asset, or fails ownership validation after deletion. Files referenced by deleted video rows remain protected. The age test is based on asset creation, so an old asset may become eligible on the next hourly pass soon after its final reference is removed. The Compose image installs FFmpeg and ffprobe, while the plain local SQLite profile leaves processing disabled unless configured. Local-mode API instances need a shared `MEDIA_DIR`. With `MEDIA_STORE=minio`, final media and resumable chunks share a private MinIO bucket while each API uses only temporary local space. The worker downloads its source from MinIO, uploads video and cover, then publishes in SQL. The API serves `/media` through the object client with HTTP Range support. Object deletion after a failed publication is best effort with a five-second bound; old unreferenced objects are reclaimed after 24 hours, and old unused asset registrations after seven days. List/stat and reference checks are repeated before removal. MinIO SDK requests use two attempts so an unavailable bucket does not occupy upload handlers for the SDK default retry duration. `/ready` remains database-only. The two-replica Compose smoke and a MinIO stop/restart drill are in `tests/integration/`; the offline `gostream-media` command now copies old referenced local files and live registered resumable chunks with SHA-256 verification and backs up/restores the dedicated object bucket. `tests/integration/media_transfer_smoke.py` has exercised a fresh MySQL database and MinIO bucket restore with the old URL and completion of an old upload session. The procedure requires a stopped writer window; production-scale recovery time and online migration remain unmeasured.

## Cache, broker, and performance

Prometheus instrumentation is active at `/metrics`, with bounded route labels and `gostream_feed_cache_total{result}` for hit/miss/error/invalidation errors. `REDIS_ADDR` enables a five-second cache for anonymous timeline/recommend/hot pages and authenticated following first pages. Cache keys include the shared Redis version, scene, viewer ID, page size, and cursor hash. Following keys also include a per-viewer version; follow/unfollow advance it, and idle version keys expire after 24 hours. Publishing, editing, deleting, liking, favoriting, commenting, and changing an author's displayed profile advance the shared version after the database write. Other authenticated scenes and following cursor pages bypass the cache. Redis errors open a five-second client circuit and fall back to database reads; failed invalidation can expose an old page for at most the five-second TTL. Play counts intentionally do not invalidate each page. The MySQL/Redis Compose profile has been built and tested with real API requests, including FFmpeg processing. The optional `observability` profile was also started: Prometheus reported `up=1` for the API and Grafana loaded the provisioned dashboard. Its configuration is baked into local images so Docker Desktop does not depend on WSL bind mounts for these files. RabbitMQ is not wired into the API. In-process and local MySQL/Redis Feed measurements are documented; no k6 or multi-host load-test results are claimed.
