# Technical design notes

These notes distinguish current behavior from the next implementation step. They are updated with source changes.

## Feed pagination and ranking

`internal/platform/feed.go` implements timeline and following feeds ordered by `created_at DESC, id DESC`; the opaque cursor carries both values so equal timestamps do not skip or duplicate a row. Feed requests fetch `limit + 1` rows to determine `has_more`. Hot ranks by `3*likes + 5*comments + 4*favorites`, tie-broken by ID. Recommendation starts with that same interaction score, adds 12 points for a video younger than 24 hours or 5 for one younger than seven days, 12 for a followed author, and 6 for an author found among the viewer's 200 most recent likes/favorites. Anonymous viewers receive the interaction and freshness parts. `recommend.go` computes the SQL ordering and the cursor score from the same weights. The recommendation cursor includes a fixed time anchor and scene, expires after 24 hours, and avoids recency buckets changing between pages. Interaction counts and preferences can still change between requests, so score-based pagination is not a stable snapshot. The strategy favors known authors and has no topic model or author-diversity control.

Following Feed is a database join. Its first page can use a short-lived, viewer-specific Redis cache; cursor pages still read SQL. This reduces repeated first-page joins but does not change the read cost of a miss or deeper pagination. A later scale stage can add a hybrid index: fan out posts into recent follower inboxes for ordinary creators, and read a creator outbox for high-follower accounts. The write path should use a durable event and idempotent batch cursor so a worker restart cannot lose or multiply fanout work.

## Interaction state

`video_actions` has a unique constraint on `(user_id, video_id, kind)`. A like/favorite transition and its denormalized video count are updated in one database transaction. The insert uses `ON CONFLICT DO NOTHING`; the count changes only when a row was inserted or removed. Repeating PUT does not increment twice, and repeating DELETE does not decrement twice. Notifications have a unique `(user_id, event_key)` constraint so retries do not create duplicate notices.

Counts are maintained synchronously in the same database. A notification and an outbox event are written in the same transaction as a new interaction or comment. The outbox worker leases rows for 30 seconds, retries failed sends with exponential delay, and marks an event dead after eight attempts. The database inbox is authoritative; local WebSocket push is a convenience. The optional Redis page cache is invalidated by advancing a version after successful interaction writes; Redis does not own counters.

## Messaging semantics

The WebSocket hub in `internal/platform/hub.go` is process-local. A message, notification, and outbox event commit before the sender receives an ACK. `(sender_id, client_id)` makes exact retries resolve to the same stored message; reusing an ID with different content is rejected. A recipient reconnect replays up to 100 unacknowledged messages; `GET /api/messages/unread` pages through the rest. Recipient ACK is an idempotent HTTP call that stores `acked_at`.

Groups have an owner, a unique membership row for each user, durable messages, and a per-member monotonically increasing read cursor. Members can read history and send; only owners can invite or remove others. Local group fanout uses the same hub; with `REDIS_ADDR`, a Pub/Sub event causes each other API instance to query current membership and deliver to its local sockets. Direct-message and outbox-notification events are relayed similarly, using committed database IDs rather than payload content. Redis subscription reconnects after interruption. Direct and group publication is best effort, so Pub/Sub outages can delay online delivery; SQL unread/history APIs recover missed data. Outbox notification publication retries failures. On reconnect, each socket receives up to 100 unacknowledged group messages in ID order, followed by `group_sync_required` when more exist; the client can then read group history. Local presence comes from active connections; with Redis, each instance refreshes an expiring per-user/per-node sorted-set entry every 30 seconds, and other instances count unexpired entries. Disconnects remove the entry and persist `last_seen_at`; a crashed node ages out within 75 seconds. Without Redis or during Redis failure, only local presence is visible. The browser offers both `gostream` and `gostream.jwt.<token>` WebSocket subprotocols; the server negotiates only the public `gostream` protocol and reads the second for authentication. The API logger records paths without query parameters. Clients should deduplicate deliveries by message ID.

## Media upload

The authenticated single-file upload handler writes to local disk using random file names and a 250 MiB request cap. A separate resumable flow creates a session, accepts 4 MiB chunks in any order, stores per-chunk SHA256 values, then assembles and hashes the full file. A database completion lease limits concurrent finalization. Incomplete chunks live beside the public media directory and expire after 24 hours; a cleanup worker removes expired data. Published video and cover URLs must belong to the current account. MP4/MOV/WebM signatures and image signatures are checked; JPEG/PNG also have their dimensions decoded.

When `FFMPEG_BIN` is set, publication and a `video_process_jobs` row commit together, with the video initially hidden as `processing`. The worker conditionally claims a five-minute database lease and handles one job at a time per instance. Before decoding, ffprobe reads the first video stream and duration with a 15-second timeout. Missing/invalid metadata, duration over 10 minutes, a side over 4096 pixels, or more than 3840×2160 pixels total permanently fails the job after one attempt. These checks apply to reported stream metadata and do not inspect every frame for later resolution changes. The four-minute FFmpeg command timeout and two encoder threads bound processing. The worker produces H.264 MP4 (AAC when the source has audio) plus a JPEG cover in a private temporary directory. It probes the output and stores its duration, width, and height with the media asset records and published video in one transaction. Output files are removed if the transaction fails or the source was replaced/deleted. An expired lease is reclaimable after a crash. Other failures retry up to three attempts with a growing delay, then mark the video `failed`; an author can resubmit the source. The job stores internal error text but the author API returns only an allowlisted failure code, which the creator page renders as a short reason. Temporary processing directories older than 24 hours are cleaned periodically. An hourly reconciliation also checks generated files in `MEDIA_DIR` after a 24-hour grace period; in batches of 100 it retains files referenced by assets, videos (including deleted rows), unfinished processing jobs, or avatars and deletes unreferenced regular files. It skips symlinks, unexpected names, and recently modified files. Database failures stop deletion. Registered media assets without active use are retained. The Compose image installs FFmpeg and ffprobe, while the plain local SQLite profile leaves processing disabled unless configured. Multiple API instances need a shared `MEDIA_DIR`; cross-host object storage remains future work.

## Cache, broker, and performance

Prometheus instrumentation is active at `/metrics`, with bounded route labels and `gostream_feed_cache_total{result}` for hit/miss/error/invalidation errors. `REDIS_ADDR` enables a five-second cache for anonymous timeline/recommend/hot pages and authenticated following first pages. Cache keys include the shared Redis version, scene, viewer ID, page size, and cursor hash. Following keys also include a per-viewer version; follow/unfollow advance it, and idle version keys expire after 24 hours. Publishing, editing, deleting, liking, favoriting, commenting, and changing an author's displayed profile advance the shared version after the database write. Other authenticated scenes and following cursor pages bypass the cache. Redis errors open a five-second client circuit and fall back to database reads; failed invalidation can expose an old page for at most the five-second TTL. Play counts intentionally do not invalidate each page. The MySQL/Redis Compose profile has been built and tested with real API requests, including FFmpeg processing. The optional `observability` profile was also started: Prometheus reported `up=1` for the API and Grafana loaded the provisioned dashboard. Its configuration is baked into local images so Docker Desktop does not depend on WSL bind mounts for these files. RabbitMQ is not wired into the API. In-process and local MySQL/Redis Feed measurements are documented; no k6 or multi-host load-test results are claimed.
